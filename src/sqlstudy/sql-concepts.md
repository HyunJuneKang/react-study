# SQL 핵심 개념 정리

이 문서는 일반 백엔드 개발자와 데이터 직무의 SQL 면접을 위한 개념서입니다. 문법 이름만 외우기보다 **어떤 문제를 해결하는지, 결과가 왜 달라지는지, 어떤 선택에 비용이 따르는지**를 설명하는 것을 목표로 합니다. SQL 문법과 동작은 MySQL, PostgreSQL, Oracle, SQL Server 등 DBMS마다 일부 차이가 있으므로 제품별 세부 사항은 공식 문서를 함께 확인해야 합니다.

## 데이터베이스 기본 구조

- **데이터베이스(Database)**: 관련 데이터를 목적에 맞게 구조화해 저장한 집합입니다.
- **DBMS(Database Management System)**: 데이터베이스를 생성·조회·수정하고 권한, 동시성, 복구를 관리하는 소프트웨어입니다. MySQL, PostgreSQL, Oracle Database 등이 해당합니다.
- **스키마(Schema)**: 테이블, 컬럼, 관계, 제약조건 등 데이터 구조에 대한 정의입니다. DBMS마다 데이터베이스와 스키마를 구분하는 방식이 조금씩 다릅니다.
- **테이블(Table)**: 데이터를 행(Row)과 열(Column) 형태로 저장하는 관계형 데이터 구조입니다.
- **행(Row, Record)**: 하나의 개체를 나타내는 데이터 한 건입니다.
- **열(Column, Attribute)**: 데이터가 가진 속성과 자료형을 정의합니다.

관계를 단순화하면 다음과 같이 이해할 수 있습니다.

```text
DBMS → Database → Schema → Table → Row / Column
```

### RDBMS와 NoSQL

**RDBMS**는 미리 정의한 스키마와 테이블 간 관계를 기반으로 데이터를 관리합니다. 트랜잭션과 데이터 정합성이 중요한 결제, 주문, 계좌 시스템에 적합합니다. 조인과 표준 SQL을 사용할 수 있지만, 복잡한 분산 확장에는 추가 설계가 필요합니다.

**NoSQL**은 Key-Value, Document, Column Family, Graph 등 다양한 모델을 사용합니다. 스키마 변화가 잦거나 대규모 수평 확장, 특정 접근 패턴에 최적화할 때 유용합니다. 대신 데이터 중복과 일관성, 조인 대체 전략을 애플리케이션에서 더 신중하게 설계해야 할 수 있습니다.

중요한 것은 어느 한쪽이 항상 우수한 것이 아니라 **데이터 관계, 정합성 수준, 조회 패턴, 확장 요구사항**에 따라 선택하는 것입니다.

## SQL 명령어 분류

| 분류 | 역할                       | 대표 명령어                            |
| ---- | -------------------------- | -------------------------------------- |
| DDL  | 데이터 구조 정의           | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`  |
| DML  | 데이터 조회·삽입·수정·삭제 | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| DCL  | 사용자 권한 제어           | `GRANT`, `REVOKE`                      |
| TCL  | 트랜잭션 제어              | `COMMIT`, `ROLLBACK`, `SAVEPOINT`      |

`SELECT`를 DML이 아닌 DQL(Data Query Language)로 별도 분류하는 자료도 있습니다. 면접에서는 분류 기준이 다를 수 있음을 언급하고 각 명령의 실제 역할을 정확히 설명하는 편이 좋습니다.

### DELETE, TRUNCATE, DROP

| 명령       | 제거 대상        | 테이블 구조 | 조건 사용         |
| ---------- | ---------------- | ----------- | ----------------- |
| `DELETE`   | 선택한 행        | 유지        | `WHERE` 가능      |
| `TRUNCATE` | 테이블의 전체 행 | 유지        | 일반적으로 불가능 |
| `DROP`     | 테이블 객체 자체 | 제거        | 불가능            |

- `DELETE`에서 `WHERE`를 생략하면 모든 행이 삭제되므로 특히 주의해야 합니다.
- `TRUNCATE`는 전체 데이터를 빠르게 비우는 용도지만 트랜잭션 처리, 로그 기록, 자동 증가 값 초기화 여부는 DBMS마다 다릅니다.
- `DROP` 이후에는 해당 테이블을 바로 조회할 수 없습니다.

## 기본 조회와 조건식

```sql
SELECT DISTINCT city
FROM customers
WHERE city IN ('서울', '부산')
ORDER BY city;
```

- `DISTINCT`: 선택한 컬럼 조합이 같은 결과 행의 중복을 제거합니다. 불필요한 조인 중복을 가리는 용도로 무조건 사용해서는 안 됩니다.
- `ORDER BY`: 결과의 정렬 순서를 보장합니다. 지정하지 않으면 저장 순서처럼 보여도 그 순서는 보장되지 않습니다.
- `LIMIT`, `TOP`, `FETCH FIRST`: 결과 행 수를 제한하며 문법은 DBMS마다 다릅니다.
- `LIKE`: `%`는 길이 0 이상의 문자열, `_`는 문자 하나를 의미하는 패턴 검색에 사용합니다.
- `BETWEEN`: 일반적으로 양쪽 경계값을 포함합니다. 날짜·시간 조건에서는 마지막 시각 처리에 주의합니다.
- `IN`: 여러 값 중 하나와 일치하는지 검사합니다.

## 집합 연산

```sql
SELECT email FROM current_members
UNION
SELECT email FROM withdrawn_members;
```

- `UNION`: 두 결과를 합치고 중복 행을 제거합니다.
- `UNION ALL`: 중복을 유지하므로 중복 제거 작업이 없는 만큼 일반적으로 더 단순하고 빠릅니다.
- 결합하는 각 `SELECT`는 컬럼 개수가 같아야 하고 대응하는 컬럼의 자료형이 호환되어야 합니다.
- `INTERSECT`는 교집합, `EXCEPT` 또는 `MINUS`는 차집합을 구하지만 지원 문법은 DBMS마다 다릅니다.

## SQL 실행 순서

일반적인 `SELECT` 문의 논리적 실행 순서는 다음과 같습니다.

```text
FROM → JOIN / ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

- `WHERE`는 행을 그룹화하기 전에 거릅니다.
- `HAVING`은 `GROUP BY` 이후 만들어진 그룹을 거릅니다.
- `SELECT` 별칭은 보통 `WHERE`에서 바로 사용할 수 없습니다. 아직 `SELECT`가 실행되기 전이기 때문입니다.

## 키와 무결성

- **Primary Key(PK)**: 테이블의 각 행을 고유하게 식별합니다. 중복과 `NULL`을 허용하지 않습니다.
- **Foreign Key(FK)**: 다른 테이블의 PK 또는 Unique Key를 참조해 관계와 참조 무결성을 유지합니다.
- **복합키**: 둘 이상의 컬럼을 묶어 행을 식별하는 키입니다. 예: `(student_id, course_id)`.
- **참조 무결성**: 자식 테이블의 FK 값이 부모 테이블의 유효한 키를 참조하도록 보장하는 규칙입니다.

### 키의 종류

- **슈퍼키**: 행을 유일하게 식별할 수 있는 컬럼의 집합입니다. 식별에 불필요한 컬럼이 포함될 수 있습니다.
- **후보키**: 최소한의 컬럼으로 행을 유일하게 식별하는 슈퍼키입니다.
- **기본키**: 후보키 중 대표로 선택한 키입니다.
- **대체키**: 후보키 중 기본키로 선택되지 않은 키입니다.
- **자연키**: 이메일, 주민번호처럼 업무상 의미가 있는 값으로 만든 키입니다.
- **대리키**: 자동 증가 번호나 UUID처럼 식별만을 위해 만든 키입니다.

Primary Key는 한 테이블의 대표 식별자이고 `NULL`을 허용하지 않습니다. Unique 제약조건은 중복을 막는 후보키 표현에 사용하며 한 테이블에 여러 개 둘 수 있습니다. `NULL` 허용 및 중복 판단 방식은 DBMS마다 차이가 있을 수 있습니다.

### 주요 제약조건

- `NOT NULL`: 값이 반드시 존재하도록 합니다.
- `UNIQUE`: 컬럼 또는 컬럼 조합의 중복을 제한합니다.
- `CHECK`: 값이 지정한 조건을 만족하도록 합니다.
- `DEFAULT`: 입력값이 없을 때 사용할 기본값을 정의합니다.
- `FOREIGN KEY`: 부모 테이블과의 참조 관계를 보장합니다.

### 테이블 관계

- **1:1**: 한 행이 상대 테이블의 한 행과 관계를 맺습니다. FK에 Unique 제약을 함께 둘 수 있습니다.
- **1:N**: 부모 한 행을 자식 여러 행이 참조합니다. 자식 테이블에 FK를 둡니다.
- **N:M**: 양쪽 모두 여러 행과 관계를 맺습니다. 두 FK를 가진 연결 테이블로 풀어냅니다.

## 조인

```sql
-- 주문이 존재하는 고객만 조회
SELECT c.customer_name, o.order_id
FROM customers c
INNER JOIN orders o ON o.customer_id = c.customer_id;

-- 주문이 없는 고객도 포함
SELECT c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;
```

- **INNER JOIN**: 양쪽 조건이 일치하는 행만 반환합니다.
- **LEFT JOIN**: 왼쪽 테이블의 모든 행을 유지하고, 오른쪽에 매칭되는 행이 없으면 `NULL`을 채웁니다.
- **CROSS JOIN**: 두 테이블의 모든 조합을 만들므로 행 수가 급증할 수 있습니다.
- `LEFT JOIN`의 오른쪽 테이블 조건을 `WHERE`에 두면 `NULL` 행이 제거되어 결과가 `INNER JOIN`처럼 바뀔 수 있습니다.

### 그 밖의 조인

- **RIGHT JOIN**: 오른쪽 테이블의 모든 행을 유지합니다. 테이블 순서를 바꾸어 `LEFT JOIN`으로 표현할 수도 있습니다.
- **FULL OUTER JOIN**: 양쪽 테이블의 모든 행을 유지하고 일치하지 않는 쪽을 `NULL`로 채웁니다.
- **SELF JOIN**: 같은 테이블을 서로 다른 별칭으로 조인합니다. 직원과 관리자처럼 자기 참조 관계를 조회할 때 사용합니다.

조인은 테이블을 단순히 옆으로 붙이는 기능이 아닙니다. 조인 키가 한쪽에서 중복되면 한 행이 여러 행과 매칭되어 결과 행 수가 늘어납니다. 따라서 결과가 예상보다 많다면 `DISTINCT`로 숨기기 전에 **관계의 카디널리티와 조인 조건**이 올바른지 확인해야 합니다.

### ON과 WHERE의 차이

```sql
-- 모든 고객을 유지하고, 결제 완료 주문만 연결
SELECT c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
 AND o.status = 'PAID';

-- 결제 완료 주문이 있는 고객만 남음
SELECT c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'PAID';
```

`INNER JOIN`에서는 같은 결과가 되는 조건도 외부 조인에서는 위치에 따라 결과가 달라질 수 있습니다.

### 대표적인 물리 조인 알고리즘

- **Nested Loop Join**: 한쪽 행마다 다른 쪽을 탐색합니다. 작은 결과 집합과 적절한 인덱스가 있을 때 효과적입니다.
- **Hash Join**: 한쪽 입력으로 해시 테이블을 만들고 같은 키를 찾습니다. 동등 조인과 비교적 큰 데이터에 유리할 수 있습니다.
- **Merge Join**: 정렬된 두 입력을 함께 순회합니다. 양쪽이 조인 키로 정렬되어 있을 때 효과적입니다.

개발자가 SQL에 알고리즘을 직접 지정하기보다는 옵티마이저가 통계와 비용을 바탕으로 선택하는 경우가 일반적입니다.

## 집계

```sql
SELECT customer_id, COUNT(*) AS order_count, SUM(amount) AS total_amount
FROM orders
WHERE status = 'PAID'
GROUP BY customer_id
HAVING COUNT(*) >= 10;
```

- `GROUP BY`는 같은 값을 가진 행을 그룹으로 묶습니다.
- 집계 함수에는 `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`가 있습니다.
- `SELECT` 절에는 그룹화한 컬럼 또는 집계한 값만 사용합니다.
- `COUNT(column)`은 `NULL`을 세지 않고, `COUNT(*)`는 행 자체를 셉니다.

## 서브쿼리와 CTE

- **서브쿼리**: 다른 SQL 문 안에 포함된 `SELECT` 문입니다.
- **상관 서브쿼리**: 바깥 쿼리의 행 값을 참조하며 행마다 평가될 수 있습니다.
- **CTE**: `WITH`로 이름을 붙인 임시 결과 집합입니다. 복잡한 쿼리를 읽기 쉽게 나누는 데 유리합니다.

```sql
WITH customer_sales AS (
  SELECT customer_id, SUM(amount) AS total_amount
  FROM orders
  GROUP BY customer_id
)
SELECT *
FROM customer_sales
WHERE total_amount >= 100000;
```

### IN과 EXISTS

- `IN`은 값이 목록 또는 서브쿼리 결과에 포함되는지 표현하기 좋습니다.
- `EXISTS`는 조건을 만족하는 행이 하나라도 존재하는지를 검사하며 상관 서브쿼리와 자주 사용합니다.
- 실제 성능은 문법만으로 단정할 수 없고 옵티마이저, 통계, 인덱스, 데이터 분포에 따라 달라집니다.
- `NOT IN`의 서브쿼리 결과에 `NULL`이 포함되면 SQL의 3값 논리 때문에 기대한 행이 나오지 않을 수 있습니다. 의도가 존재하지 않음을 확인하는 것이라면 `NOT EXISTS`를 고려합니다.

## NULL과 조건식

- `NULL`은 0이나 빈 문자열이 아니라 **값을 알 수 없거나 존재하지 않음**을 뜻합니다.
- `NULL` 비교에는 `IS NULL`, `IS NOT NULL`을 사용합니다.
- `COALESCE(a, b, c)`는 앞에서부터 `NULL`이 아닌 첫 값을 반환합니다.
- `CASE WHEN`은 SQL의 조건 분기입니다.

```sql
SELECT order_id,
       CASE WHEN amount >= 100000 THEN 'VIP' ELSE 'NORMAL' END AS grade
FROM orders;
```

SQL 조건식은 `TRUE`, `FALSE`뿐 아니라 `UNKNOWN`을 포함하는 **3값 논리**를 사용합니다. `NULL = NULL`의 결과도 `TRUE`가 아니라 `UNKNOWN`이므로 `WHERE` 조건을 통과하지 않습니다.

## 윈도 함수

윈도 함수는 여러 행을 참고하지만 `GROUP BY`처럼 행을 하나로 줄이지 않습니다.

```sql
SELECT employee_name, department_id, salary,
       DENSE_RANK() OVER (
         PARTITION BY department_id
         ORDER BY salary DESC
       ) AS salary_rank
FROM employees;
```

- `PARTITION BY`: 그룹을 나눕니다.
- `ORDER BY`: 각 그룹의 순서를 정합니다.
- `ROW_NUMBER`: 동점이어도 순번을 다르게 부여합니다.
- `RANK`: 동점은 같은 순위, 다음 순위는 건너뜁니다.
- `DENSE_RANK`: 동점은 같은 순위, 다음 순위를 건너뛰지 않습니다.
- `LAG`, `LEAD`: 이전/다음 행 값을 가져옵니다.

## 정규화와 역정규화

- **정규화**: 데이터 중복을 줄이고 삽입·갱신·삭제 이상을 줄이도록 테이블을 분리하는 설계 과정입니다.
- **1NF**: 컬럼 값이 원자값이어야 합니다.
- **2NF**: 부분 함수 종속을 제거합니다.
- **3NF**: 이행 함수 종속을 제거합니다.
- **역정규화**: 조회 성능이나 단순화를 위해 의도적으로 중복을 허용합니다. 데이터 일관성 유지 비용이 증가합니다.

## 인덱스와 실행 계획

- **인덱스**: 원하는 행의 위치를 빠르게 찾도록 만든 보조 자료구조입니다.
- 조회·정렬·조인에 도움을 줄 수 있지만, 인덱스도 저장 공간을 차지하고 `INSERT`/`UPDATE`/`DELETE` 비용을 늘립니다.
- **복합 인덱스**는 앞쪽 컬럼부터 조건에 활용되는 경우가 많으므로 컬럼 순서가 중요합니다.
- **Full Table Scan**은 테이블 전체를 읽는 방식입니다. 작은 테이블에서는 더 효율적일 수도 있습니다.
- **실행 계획**으로 실제 접근 방식, 예상 행 수, 조인 방식, 비용을 확인해 튜닝 근거를 찾습니다.

### 인덱스 설계 핵심

- **선택도**가 높은 컬럼은 전체 행 중 적은 행을 찾을 수 있어 인덱스 후보가 되기 쉽습니다. 성별처럼 값 종류가 매우 적은 컬럼은 단독 인덱스 효과가 제한적일 수 있습니다.
- 복합 인덱스 `(a, b, c)`는 일반적으로 선두 컬럼부터 활용되는 조건에 유리합니다. 자주 사용하는 필터, 조인, 정렬 조건을 함께 고려해 순서를 정합니다.
- 쿼리에 필요한 컬럼을 인덱스만으로 충족하는 **Covering Index**는 테이블 접근을 줄일 수 있지만 인덱스 크기와 쓰기 비용이 증가합니다.
- 컬럼에 함수를 적용하거나 암시적 형 변환이 발생하면 인덱스를 효율적으로 사용하지 못할 수 있습니다.
- 인덱스가 있어도 조회 범위가 너무 넓으면 전체 스캔이 더 저렴하다고 옵티마이저가 판단할 수 있습니다.

클러스터형 인덱스는 테이블 데이터의 물리적 또는 논리적 배치와 밀접하게 연결되고, 비클러스터형 인덱스는 별도 구조에서 행 위치를 가리킵니다. 정확한 저장 구조와 개수 제한은 DBMS마다 다릅니다.

### 실행 계획에서 확인할 내용

1. Table Scan인지 Index Scan/Seek인지
2. 예상 행 수와 실제 행 수 차이가 큰지
3. 어떤 조인 방식과 조인 순서를 선택했는지
4. 정렬, 임시 공간, 키 조회 등 비용이 큰 연산이 있는지
5. 조건절이 가능한 한 일찍 적용되는지

### 대용량 페이징

```sql
-- 뒤 페이지로 갈수록 건너뛰는 행이 많아질 수 있음
SELECT *
FROM orders
ORDER BY order_id
LIMIT 20 OFFSET 100000;

-- 마지막으로 본 키 이후부터 조회하는 Seek 방식
SELECT *
FROM orders
WHERE order_id > :last_order_id
ORDER BY order_id
LIMIT 20;
```

Seek 방식은 임의 페이지 이동에는 제약이 있지만 연속적인 목록 조회에서 큰 OFFSET 비용을 줄일 수 있습니다.

## 트랜잭션과 동시성

- **트랜잭션**: 모두 성공하거나 모두 실패해야 하는 작업 단위입니다.
- **ACID**: 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability).
- `COMMIT`은 변경을 확정하고, `ROLLBACK`은 변경을 되돌리며, `SAVEPOINT`는 트랜잭션 안의 중간 복구 지점입니다.
- **Dirty Read**: 커밋되지 않은 데이터를 읽는 현상입니다.
- **Non-repeatable Read**: 같은 행을 다시 읽었는데 다른 트랜잭션의 커밋으로 값이 달라지는 현상입니다.
- **Phantom Read**: 같은 조건으로 다시 조회했는데 행의 개수나 구성 자체가 달라지는 현상입니다.
- **데드락**: 트랜잭션들이 서로가 가진 락을 기다려 진행하지 못하는 상태입니다. 일정한 자원 접근 순서와 짧은 트랜잭션으로 예방합니다.

### ACID

- **Atomicity(원자성)**: 트랜잭션의 작업은 전부 반영되거나 전부 취소되어야 합니다.
- **Consistency(일관성)**: 트랜잭션 전후에 제약조건과 업무 규칙을 만족하는 유효한 상태를 유지해야 합니다.
- **Isolation(격리성)**: 동시에 실행되는 트랜잭션이 서로의 중간 상태에 부적절하게 영향을 주지 않아야 합니다.
- **Durability(지속성)**: 커밋된 결과는 장애가 발생해도 복구할 수 있어야 합니다.

### 트랜잭션 격리 수준

| 격리 수준        | Dirty Read | Non-repeatable Read | Phantom Read |
| ---------------- | ---------- | ------------------- | ------------ |
| READ UNCOMMITTED | 가능       | 가능                | 가능         |
| READ COMMITTED   | 방지       | 가능                | 가능         |
| REPEATABLE READ  | 방지       | 방지                | 표준상 가능  |
| SERIALIZABLE     | 방지       | 방지                | 방지         |

격리 수준을 높이면 데이터 일관성은 강해지지만 락 대기, 충돌, 처리량 저하가 커질 수 있습니다. 실제 현상 방지 방식은 MVCC와 DBMS 구현에 따라 표준 표와 다를 수 있습니다.

### 공유 락과 배타 락

- **공유 락(Shared Lock)**: 읽기를 위한 락입니다. 여러 트랜잭션이 동시에 공유 락을 가질 수 있지만 일반적으로 배타 락과 충돌합니다.
- **배타 락(Exclusive Lock)**: 변경을 위한 락입니다. 다른 공유 락 또는 배타 락과 충돌해 동시에 같은 데이터를 변경하지 못하게 합니다.

공유·배타 락은 **DB가 획득하는 락의 종류**이고, 낙관적·비관적 락은 **애플리케이션이 충돌을 다루는 전략**이라는 차이가 있습니다.

### 낙관적 락과 비관적 락

**낙관적 락**은 충돌이 드물다고 가정하고 실제 DB 락을 오래 유지하지 않습니다. 수정 시 버전 값이 여전히 같은지 확인하고, 영향받은 행이 없다면 다른 트랜잭션이 먼저 수정했다고 판단해 재시도 또는 사용자 안내를 수행합니다.

```sql
UPDATE products
SET stock = stock - 1,
    version = version + 1
WHERE product_id = 1
  AND version = 5;
```

**비관적 락**은 충돌 가능성이 높다고 보고 데이터를 읽을 때부터 잠급니다. 재고 1개, 좌석 1개처럼 동시 변경 충돌 비용이 큰 상황에서 고려할 수 있습니다.

```sql
SELECT stock
FROM products
WHERE product_id = 1
FOR UPDATE;
```

비관적 락은 충돌을 직접 막지만 락 대기와 데드락 가능성이 있고, 낙관적 락은 동시 처리에 유리하지만 충돌 시 재시도 정책이 필요합니다.

### MVCC

MVCC(Multi-Version Concurrency Control)는 데이터의 여러 버전을 이용해 읽기와 쓰기의 충돌을 줄이는 방식입니다. 독자는 자신의 트랜잭션에서 볼 수 있는 일관된 버전을 읽고, 작성자는 새 버전을 만듭니다. 가시성 규칙과 오래된 버전 정리 방식은 DBMS마다 다릅니다.

### 데드락 예방과 대응

- 여러 테이블과 행을 항상 같은 순서로 접근합니다.
- 트랜잭션 범위를 짧게 유지합니다.
- 적절한 인덱스로 잠그는 행의 범위를 줄입니다.
- 외부 API 호출처럼 오래 걸리는 작업을 락을 잡은 채 수행하지 않습니다.
- DBMS가 한 트랜잭션을 중단하면 애플리케이션에서 안전한 재시도를 고려합니다.

## 보안: SQL Injection

사용자 입력을 SQL 문자열에 그대로 이어 붙이면 악성 SQL이 실행될 수 있습니다.

- Prepared Statement / Parameterized Query를 사용합니다.
- 입력값을 검증합니다.
- DB 계정 권한을 최소화합니다.
- 오류 메시지에 SQL 내부 정보를 노출하지 않습니다.

## 참고: DBA·데이터 엔지니어 심화 영역

아래 주제는 일반적인 SQL 개발 면접의 핵심 범위보다 DB 운영과 대규모 데이터 플랫폼 설계에 더 가깝습니다. 발표 본문에서는 참고 영역으로 두고, DBA 또는 데이터 엔지니어 직무를 준비할 때 심화 학습합니다.

### 파티셔닝(Partitioning)

큰 테이블을 날짜, 범위, 해시 등의 기준으로 여러 파티션으로 나누어 관리하는 방식입니다. 조회 조건이 파티션 키를 포함하면 필요한 파티션만 읽는 **파티션 프루닝**으로 성능과 관리 효율을 높일 수 있습니다. 잘못된 파티션 키 선택, 데이터 쏠림, 파티션이 지나치게 많은 경우는 오히려 성능과 운영 복잡도를 높일 수 있습니다.

### 샤딩(Sharding)

데이터를 여러 DB 서버에 수평 분할해 저장하는 방식입니다. 한 서버의 용량과 처리량 한계를 넘어설 때 사용합니다. 예를 들어 `user_id`를 기준으로 사용자 데이터를 여러 샤드에 나눌 수 있습니다. 샤드 간 조인, 전역 트랜잭션, 재샤딩, 데이터 불균형이 어려운 점입니다.

### 복제(Replication)

원본 DB의 데이터를 하나 이상의 복제본에 동기화하는 방식입니다. 읽기 부하 분산, 고가용성, 장애 복구에 활용합니다. 대표적으로 원본에서 쓰기를 처리하고 복제본에서 읽기를 처리하는 구조가 있습니다. 비동기 복제에서는 복제 지연으로 인해 최신 데이터가 즉시 보이지 않을 수 있습니다.

### 백업과 복구(Backup & Recovery)

장애, 사용자 실수, 데이터 손상에 대비해 데이터를 복원할 수 있도록 하는 운영 체계입니다.

- **전체 백업**: 데이터베이스 전체를 백업합니다.
- **증분/차등 백업**: 마지막 백업 이후 변경된 데이터만 추가로 백업합니다.
- **트랜잭션 로그 백업**: 특정 시점으로 복구(Point-in-Time Recovery)하는 데 활용합니다.
- **RPO**: 장애 시 허용할 수 있는 데이터 손실 범위입니다.
- **RTO**: 장애 후 서비스를 복구해야 하는 목표 시간입니다.

백업 파일을 만드는 것만으로는 충분하지 않습니다. 실제 복구 절차를 정기적으로 점검하고 복구 시간을 검증해야 합니다.
